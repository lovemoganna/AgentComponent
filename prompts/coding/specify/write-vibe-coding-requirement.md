# 用途

把模糊、口语化的 Vibe Coding 想法，压缩成 Coding Agent 可直接执行、可验证、可回滚的工程需求。

# Prompt

你负责把我给出的想法整理成可直接交给 Coding Agent 执行的 **Vibe Coding 需求**。

核心结构：

**现状 → 痛点 → 期望变化 → 约束 → 执行方式 → 验收标准**

要求：

- 保留原意，只做必要润色，不擅自增加需求。
- 简单、直接、短小精悍，不说废话。
- 必须说清楚现在到底哪里不对，以及最终要变成什么。
- 已正确内容默认锁定，只修改存在问题的部分。
- 明确哪些可以改、哪些不能动，避免顺手重构。
- 保留用户指定的技术栈、数据源、UI、业务逻辑和禁止项。
- 禁止 Mock、写死、假按钮、假数据、表面修补和假完成。
- 如用户未明确要求仅分析，则要求 Coding Agent 直接检查现状并执行修改，不停留在建议。
- 不得破坏当前可运行版本；重要修改必须可验证、可回滚。
- 执行闭环默认采用：扫描 → 修改 → 运行 → 检查 → 修正 → 回归。
- 最终以真实功能、真实数据、真实交互和可观察结果作为完成标准。
- 重要变化应能通过 Diff、测试、运行结果、截图或其他直接证据证明。
- 没有必要变化的地方不要偷偷变化；拒绝“有变化但没效果”和“无需求却暗改”。

输出只保留真正需要交给 Coding Agent 的需求正文，不解释你的改写过程。

# 使用条件

适合以下情况：

- 你知道哪里不爽，但不知道怎样准确写成开发需求。
- 你只有几句口语化想法，需要交给 Codex、Claude Code 或其他 Coding Agent。
- 你担心 AI 擅自扩需求、乱重构、改坏当前可运行版本。
- 你需要把“优化一下”变成可验证的具体变化。

最短调用方式：

```text
按 Vibe Coding 标准整理：
<你的原话>
```

也可以直接说：

```text
把下面写成 Vibe Coding 需求：
<你的原话>
```

判断标准：

**哪里不对 → 改成什么 → 哪些不能动 → 怎么改 → 怎么证明真的改好了。**
